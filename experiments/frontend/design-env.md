# 실험 5: 환경 개선

> 2026-11-03 사용자 확인. 사람이 사용자 혼자라 팀 상황은 가상으로 정한다.

## 질문
- 공통 코드를 고칠 때마다 리뷰를 기다려야 한다면, 어떤 설계가 그 병목을 줄이고 개발자가 보기에도 좋은 코드를 남길까?

## 고정값
- 시작 코드: 앞 실험의 "필요할 때만 분리" 구조 (`starter-role/B`)
- 모델: Sonnet 5.5, effort low, Max 구독으로 실행
- 장면마다 새 세션으로, 같은 시작 코드에서 출발한다
- 비용과 점수 채점은 하지 않는다. 숨은 테스트는 화면이 깨졌는지만 본다

## 비교할 설계 (각 1회)
- **A. 옵션형:** 공통 컴포넌트에 옵션을 더해 간다
- **B. 조합형:** 작은 조각과 `children`을 주고 화면에서 조립한다
- **C. 화면 먼저:** 화면 폴더에 먼저 두고, 두 번째 화면에서 필요할 때 공통으로 올린다

## 가상의 팀
- 공통 담당 1명: `src/ui`와 토큰을 관리하고 리뷰한다
- 화면 담당 2명: 각자 다른 화면을 만든다
- 나중에 합류하는 새 팀원 1명: 기존 코드를 모른다

## 장면
1. 없는 변형이 급히 필요함: 코드는 실제, 대기는 상상
2. 공통 담당이 내부를 고침: 코드는 실제, 영향은 판단
3. 두 사람이 동시에 고침: 브랜치 2개를 실제로 병합
4. 새 팀원이 비슷한 화면을 만듦: 안내를 받지 않은 새 세션으로 실행
5. 기능을 뺌: 화면 하나를 실제로 삭제

## 변경 쌓기
- 장면은 모두 같은 시작 코드에서 출발해 변경이 쌓인 뒤를 보지 못했다. 사용자가 C는 나중에 가장 힘들 것 같다고 봐서 이어서 비교한다
- 설계마다 변경 요청 8개를 차례로 쌓는다. 요청마다 새 세션이고, 앞 세션의 코드만 이어받는다
- 마지막 요청 1개로 앱 전체 모양을 바꾼다
- 요청은 `task/design/stack.md`, 실행은 `bench/run-stack.mjs`

## 개발자 관점의 판단 기준
- 찾기: 무언가를 고치려 할 때 어디를 열어야 할지 바로 보이는가
- 변경 범위: 고친 코드가 어느 화면까지 영향을 주는지 알 수 있는가
- 공통 코드의 모양: 옵션이 늘어 읽기 어려워지지 않는가
- 경계: 의존 방향이 한쪽으로 유지되는가
- 리뷰: 변경분을 읽고 판단하기 쉬운가, 담당자의 리뷰가 꼭 필요한 변경인가
- 지우기: 기능을 뺄 때 깔끔하게 지워지는가

일하는 방식을 겹쳐서, 같은 코드가 "누구나 고치는 팀"과 "담당이 나뉜 팀"에서 각각 좋은지도 판단한다.

## 판단하는 사람
- 에이전트가 변경분을 나란히 정리하고 근거를 붙인 초안을 쓴다
- 최종 판단은 사용자가 내린다. 결과 문서에 누구의 판단인지 구분해서 적는다

## 한계
실제 리뷰 대기 시간이나 팀원이 느끼는 답답함은 이 실험으로 볼 수 없습니다. 또 에이전트는 사람 팀처럼 일하지 않아서, 일하는 방식을 글로 적어 줘도 그것은 흉내일 뿐입니다. 여기서 확인되는 것은 "이 방식에 맞춘 환경이 코드에 어떤 차이를 남기는가"까지입니다.
