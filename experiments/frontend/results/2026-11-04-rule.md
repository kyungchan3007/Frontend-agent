# 공통으로 올리는 기준: 한 줄 규칙 · 예시 문서 · 린트

> 설계는 [design-env.md](../design-env.md), 변경분과 최종 코드는 [design-stack/](design-stack/) · [design-code/](design-code/).
> 판단은 **에이전트 초안**입니다. 사용자 판단은 아직 받지 않았습니다.

## 조건
모두 설계 D(상태는 Props, 내용은 children)의 같은 앱에서 시작했고, 각 1번입니다.

- **D:** 한 줄 규칙만 준다. 앞의 실행을 그대로 썼다
- **D2:** D + [판단 예시 문서](../task/design/rule-examples.md)
- **D3:** D2 + [린트](../task/design/lint-rule.mjs)

## 결과

| | D | D2 | D3 |
|---|---|---|---|
| 8개 중 공통을 고친 요청 | 2개 | 3개 | 3개 |
| 앱 전체 변경에서 고친 파일 | 8개 | 5개 | 5개 |
| 선택 점을 처음 넣은 곳 | 화면 3개 | `Chip` | `Chip` |
| 동시 작업 | 표시 겹침 | 표시 겹침 | 표시 겹침 |

- 세 조건 모두 변경 쌓기 뒤 숨은 테스트 44개와 타입 검사를 통과했다
- 스피너는 세 조건 모두 `Button`의 `loading`으로 처음부터 공통에 들어갔다
- `Button`에 늘어난 것은 세 조건 모두 옵션 `loading`과 변형 `dangerOutline`이다
- D는 요청 5에서 선택 점을 화면 3곳에 넣고 요청 8에서 한 번 더 복사한 뒤, 요청 9에서 `Chip`으로 옮겼다. D2 · D3는 요청 5에서 `Chip` 하나만 고쳤다

## 린트
D3의 변경 쌓기 9개 요청과 동시 작업 기록에서 린트 오류 문구가 한 번도 나오지 않았다. 잘못된 코드를 넣어 보면 잡히는 것은 확인했지만, 이번 실행에서는 막은 일이 없었다. 이번 결과로는 린트의 효과를 말할 수 없다.

## 동시 작업
기준을 줘도 표시가 겹치는 문제는 그대로였다.

- **D2:** 반복 칩에만 넣으라는 점을 `Chip` 안에 넣어 모든 칩에 들어갔다. 홈의 표준 과목 칩은 ✓는 화면에서, 점은 `Chip`에서 받아 함께 표시된다
- **D3:** 표준 과목 칩에만 넣으라는 ✓를 `Chip` 안에 넣어, 계획 추가의 반복 칩에 ✓와 점이 함께 표시된다
- 예시 문서의 "다른 화면의 모습이 달라지면 안 된다"를 두 번 모두 지키지 않았다. 세 조건 모두 병합 충돌은 없었다

테스트 실패(D2 8개, D3 9개)는 칩 글자가 바뀌어 테스트가 찾지 못한 것으로 보이며, 앞의 실험과 같은 원인으로 판단했다. D2 · D3에서 직접 확인하지는 않았다.

## 판단 초안
- **예시 문서:** 짧은 문서 하나로 복사 없이 처음부터 `Chip`에 넣었고, 앱 전체 변경은 옵션형과 같은 5개 파일이 됐다. `Button` 옵션도 적어서, 지금까지 비교한 것 중 가장 낫게 보인다
- **린트:** 이번에는 하는 일이 없었다. 처음부터 더할 이유는 찾지 못했다
- **남은 문제:** 한 화면에 필요한 표시를 공통에 넣어 다른 화면까지 바뀌는 일은 문서로 막지 못했다. 코드 형태로는 멀쩡해서 린트로 잡기도 어렵다. 화면을 비교하는 검사나 리뷰가 필요한지 볼 만하다

## 사용자 판단
- **예시 문서:** 있으면 좋다. 현업에서는 예시 문서를 따로 두지 않았던 것 같다
- **`Chip` 안에 넣기:** 화면마다 다를 것 같아서 항상 맞다고 보지 않는다

## 화면마다 다른 경우까지 나눈 표
사용자가 `Chip` 안에 넣는 것은 화면마다 다를 것 같다고 해서, 경우를 나눈 [표](../task/design/rule-examples-2.md)를 예시 문서로 주고 동시 작업 장면을 2번 돌렸다(D4 · D5).

| | 예시 문서 (D2 · D3) | 표 (D4 · D5) |
|---|---|---|
| 한 화면용 표시를 `Chip`에 넣음 | 2번 중 2번 | 2번 중 0번 |
| 다른 화면의 칩까지 바뀜 | 2번 중 2번 | 2번 중 0번 |
| 병합 충돌 | 없음 | 없음 |

- 네 세션 모두 ✓와 점을 화면의 `children`에 넣거나(D4), 작은 컴포넌트 `CheckMark`로 만들었다(D5)
- 테스트 실패 8개는 ✓가 칩 글자를 바꾼 것과 같은 항목이다. 반복 칩을 찾는 P6은 이번에 통과했다
- D4는 스피너를 화면에 직접 넣었고, D5는 `Button`에 `loading`을 더했다. 표로도 이 판단은 갈렸다
- D5는 공통 묶음(`index.js`)을 거치지 않고 `CheckMark`를 바로 가져왔다

표의 첫 문장이 이 장면의 실패를 보고 쓴 것이라 이 장면에 유리하다. 그래서 여러 화면에 쓰는 점이 다시 복사되는지 변경 쌓기도 돌렸다(D4 1번).

| | 한 줄 규칙 (D) | 예시 문서 (D2) | 표 (D4) |
|---|---|---|---|
| 8개 중 공통을 고친 요청 | 2개 | 3개 | 3개 |
| 앱 전체 변경에서 고친 파일 | 8개 | 5개 | 6개 |
| 그중 화면 파일 | 4개 | 0개 | 0개 |
| 선택 점의 모양이 있는 곳 | `Chip` (처음엔 화면) | `Chip` | `ChipDot` |
| 동시 작업에서 다른 화면이 바뀜 | 예 | 예 | 아니요 (2번 중 0번) |

- 숨은 테스트 44개와 타입 검사를 통과했다
- 걱정한 복사는 생기지 않았다. 요청 5에서 작은 컴포넌트 `ChipDot`을 만들고, 화면은 `{on && <ChipDot />}`로 넣었다
- 요청 8의 새 세션도 `ChipDot`을 찾아 썼다
- 앱 전체 변경은 `ChipDot`이 파일 하나로 늘어 6개지만, 모두 공통 파일이라 화면은 고치지 않았다
- 대신 `{on && <ChipDot />}`이 화면 4곳에 반복된다

초안: 표가 지금까지 가장 균형이 좋아 보인다. 동시 작업의 겹침을 막으면서 앱 전체 변경도 공통 파일로 끝났다. 다만 표는 두 실패를 본 뒤 썼고, 변경 쌓기는 1번뿐이다.

## 한계
- **기준을 문제를 본 뒤에 썼다.** 예시 문서는 선택 점 문제를 본 뒤 작성했다. 스피너나 점이라는 단어는 쓰지 않았지만 "상태에 항상 따라오는 표시"라는 항목은 요청 5에 잘 맞는다. 실제 팀이 미리 쓴 문서보다 유리했을 수 있다
- 조건마다 1번이고, D는 다른 시점에 돌린 실행이다
- 요청의 수와 순서는 직접 정했다

실제 리뷰 대기 시간이나 팀원이 느끼는 답답함은 이 실험으로 볼 수 없습니다. 또 에이전트는 사람 팀처럼 일하지 않아서, 일하는 방식을 글로 적어 줘도 그것은 흉내일 뿐입니다.

## 실행 기록
- D2 · D3 시작 앱은 D의 앱을 그대로 복사했고, 숨은 테스트 44개를 통과했다
- D3의 린트는 시작 코드에서 통과했고, 일부러 틀린 코드에서는 오류를 냈다
- D5의 화면 담당 1 세션은 기록에 오류로 표시됐지만 작업을 마쳤다. 마지막 결과 줄을 읽지 못한 것으로 보이고, 게이트를 직접 돌리는 명령은 권한에 막혔다. 병합본은 빌드되고 위 8개 외 테스트를 통과했다
- 표준 과목 칩의 ✓는 D 계열 모두 홈만 고쳤고, 과목 관리 화면은 고치지 않았다. 요청이 "표준 과목 칩"이라 범위가 모호했다
- 선택 점 파일 수는 D3에서 자동 집계가 색 이름 차이(`bg-inverse`)로 빠져 코드를 직접 읽어 확인했다
