# 환경 개선: 설계 3개를 가상의 팀 장면으로 비교

> 설계는 [design-env.md](../design-env.md), 변경분은 [design-code/](design-code/).
> 판단은 **에이전트 초안**입니다. 사용자의 판단을 받으면 함께 적습니다.

## 설계
- **A. 옵션형:** 공통 컴포넌트에 옵션을 더해 간다
- **B. 조합형:** 작은 조각을 주고 화면에서 조립한다
- **C. 화면 먼저:** 화면 폴더에 먼저 두고, 두 번째 화면에서 필요할 때 공통으로 올린다

## 한눈에 보기

| 장면 | A | B | C |
|---|---|---|---|
| 1. 없는 변형 | 공통 고침 | 화면만 | 화면 + 새 파일 3개 |
| 2. 내부 변경 | 공통만, 카드까지 반영 | 공통만, 카드 빠짐 | 공통만, 카드 빠짐 |
| 3. 동시 작업 | 충돌 파일 2개 | 충돌 없음 | 충돌 없음 |
| 4. 새 팀원 | 부품 재사용 | 부품 재사용 | 부품 재사용, 공통 승격 |
| 5. 기능 삭제 | 공통 정리 필요 | 공통 정리 필요 | 공통 컴포넌트 그대로 |

## 장면 1: 없는 변형이 급히 필요함 (코드는 실제, 대기는 상상)
- **A:** `Button.jsx`에 `loading`, `icon`, `caption` 옵션을 더했다. 화면 변경은 한 줄씩이다
- **B:** 공통 코드를 고치지 않았다. 스피너와 아이콘을 화면에 직접 썼고, 긴 `className`이 그대로 남았다
- **C:** 공통 코드를 고치지 않았다. `SaveButton`, `AddButton`, `StartButton`을 화면 폴더에 만들었다. 각각 한 곳에서만 쓴다

초안:
- A는 화면이 가장 읽기 좋지만, 요청 하나에 옵션이 3개 늘었고 모든 변경이 공통 담당의 리뷰를 거친다
- B는 기다리지 않아도 되지만, 버튼 한 줄이 길어 읽기 어렵다
- C도 기다리지 않아도 되지만, 한 번 쓰는 파일이 늘고 버튼을 찾을 때 한 단계 더 들어가야 한다

## 장면 2: 공통 담당이 내부를 고침 (코드는 실제, 영향은 판단)
- 세 설계 모두 공통 코드만 고쳤다
- **A:** 카드 · 목록 항목의 모양도 `Pressable` 옵션에 있어 함께 바뀌었다
- **B · C:** `Button`과 시트만 바뀌었다. 카드와 목록 항목은 화면에 `rounded-lg`로 남아 함께 바뀌지 않았다

초안:
- 앱 전체를 바꿀 때는 A가 가장 믿을 만하다. B · C는 공통 코드를 고쳐도 화면에 흩어진 모양은 따로 찾아야 한다
- 요청의 손잡이는 이미 있어서 크기만 바뀌었다

## 장면 3: 두 사람이 동시에 고침 (실제)
- **A:** `Button.jsx`, `Chip.jsx`에서 충돌했다. 두 사람 모두 같은 옵션 자리와 같은 함수 인자를 고쳤다
- **B · C:** 충돌 없이 병합됐다. 각자 자기 화면만 고쳤다

초안:
- 이번 비교에서 가장 뚜렷한 차이다. A의 충돌은 둘 다 살리면 되는 쉬운 충돌이지만, 사람이 손으로 풀어야 한다
- B · C는 충돌은 없는 대신 스피너가 화면마다 따로 남고, 선택된 칩의 표시도 화면마다 달라졌다. 다만 칩 표시가 다른 것은 요청이 그랬기 때문이다

## 장면 4: 새 팀원이 비슷한 화면을 만듦 (안내 없는 새 세션)
- 세 설계 모두 버튼 · 입력 · 시트 · 토글을 직접 만들지 않고 가져다 썼다
- **A:** 최대 길이 15를 파일에 직접 적고 오류 문구도 새로 썼다. `shared.ts`의 규칙을 쓰지 않았다
- **B:** `shared.ts`의 규칙을 썼다. 과목 선택은 플래너의 목록과 달리 칩으로 만들었다
- **C:** `shared.ts`의 규칙을 썼다. 플래너에만 있던 `Toggle`을 `src/ui`로 옮겼다. 두 번째 화면에서 옮긴다는 규칙과 같다
- **A · C:** 플래너의 과목 선택 목록을 비슷하게 다시 썼다

초안:
- 부품 재사용은 설계와 상관없이 잘 됐다. 코드에 있는 부품을 보고 따라간 것으로 보인다
- 설계보다 규칙의 위치와 화면끼리의 비슷한 코드가 더 문제다. 이 차이는 설계 때문이라고 보기 어렵다

## 장면 5: 기능을 뺌 (실제)
- 세 설계 모두 쓰지 않는 공통 코드와 `plan` 언급을 남기지 않았다
- **A:** `Toggle` 파일과 내보내기를 지우고, `Pressable`의 옵션 2개도 지웠다
- **B:** `Toggle` 파일과 내보내기를 지웠다
- **C:** 화면 폴더와 API만 지웠다. `Toggle`이 폴더 안에 있어 공통 컴포넌트는 그대로다
- 세 설계 모두 플래너만 쓰던 `--color-caution-strong` 토큰과 `Plan` 타입을 지웠다

초안:
- C가 가장 깔끔하다. A는 플래너에서만 쓰던 옵션까지 공통에 남아 있어서, 지우는 일에도 공통 담당이 필요하다

## 초안 정리

- **누구나 공통 코드를 고치는 팀:** A가 맞아 보입니다. 변경이 한곳에 모이고, 충돌은 작아서 풀 수 있습니다
- **담당이 나뉜 팀:** C가 맞아 보입니다. 화면 담당이 기다리지 않고 끝낼 수 있고, 지우기도 쉽습니다
- **B:** 기다리지 않아도 되는 점은 C와 같지만, 화면 코드가 가장 읽기 어려웠습니다. 이번에는 가장 덜 끌렸습니다

이 앱에서 볼 때 C의 약점은 앱 전체를 바꿀 때 화면에 흩어진 모양입니다. 그래서 다음에는 "모양을 정하는 값은 공통에, 새 변형은 화면에 먼저" 같은 A와 C의 혼합도 살펴볼 만하다고 봤습니다. 이번에 비교한 내용은 아닙니다.

## 사용자 판단
- **A:** 가장 좋아 보인다. 다만 팀원들끼리 미리 소통해야 한다
- **B:** 하고 싶지 않은 방식이다. 내가 쓴 코드를 다른 팀원이 보면 이해하기 어려울 것 같다. 반대로 무언가 늘어나야 할 때는 새로 만들면 되니 더 쉬울 수도 있어서, 아직 판단하지 못했다
- **C:** 나중에 가장 힘들 것 같다

변경을 쌓은 결과를 본 뒤 사용자가 이 결과로 README를 정리하기로 했다.

초안과 다른 점: 초안은 담당이 나뉜 팀에 C를 골랐지만, 사용자는 C를 가장 힘들 것으로 봤다. 이번 장면은 모두 같은 시작 코드에서 출발해서, 변경이 쌓인 "나중"은 비교하지 못했다.

## 변경을 쌓은 뒤

C가 나중에 가장 힘들 것 같다는 판단을 확인하려고, 변경 요청 8개를 이어서 쌓고 마지막에 앱 전체 모양을 바꿨습니다. 요청은 [stack.md](../task/design/stack.md), 변경분과 최종 코드는 [design-stack/](design-stack/)에 있습니다.

| | A | B | C |
|---|---|---|---|
| 8개 중 공통을 고친 요청 | 5개 | 0개 | 1개 |
| 마지막 변경에서 고친 파일 | 5개 | 9개 | 11개 |
| 스피너가 있는 파일 | 1개 | 3개 | 1개 |
| 선택 점이 있는 파일 | 1개 | 4개 | 4개 |
| 한 곳에서만 쓰는 새 파일 | 0개 | 0개 | 1개 |

- 세 설계 모두 숨은 테스트 44개와 타입 검사를 통과했고, 마지막 변경이 남긴 옛 크기도 없었다
- 시험 일정 화면(요청 8)은 세 설계 모두 공통 코드를 고치지 않고 만들었다

초안:
- **A:** 공통을 고친 요청은 앞쪽에 몰렸고, 요청 7 · 8은 있는 옵션으로 끝났다. `Button` 옵션은 `loading`, `plusIcon`, `subLabel`과 변형 1개가 늘었지만 읽지 못할 정도는 아니었다. 마지막 변경은 공통 파일만 고쳐서 가장 편했다
- **B:** 8개 요청 모두 기다릴 일이 없어 늘리기는 가장 쉬웠다. 대신 스피너와 점이 화면마다 복사됐고, 버튼 한 줄이 가장 길어졌다
- **C:** 걱정했던 한 번 쓰는 파일은 거의 쌓이지 않았다. 스피너는 규칙대로 두 번째 화면에서 공통으로 올렸다. 하지만 점은 세 화면에 동시에 들어갔는데도 올리지 않아 B와 같아졌다. `보관` 버튼도 공통 `Button`을 쓰지 않고 따로 만들었다

C의 어려움은 파일이 쌓이는 것보다, **공통으로 올릴지를 작업자가 그때그때 판단해야 하는 것**으로 보입니다. 같은 규칙에서 스피너는 올리고 점은 올리지 않았습니다.

갱신한 초안:
- A가 앞의 초안보다 낫게 보입니다. 공통을 고치는 일이 앞쪽에 몰린다면, 미리 소통할 일도 초반에 몰릴 수 있습니다. 다만 이번에는 다른 사람과 동시에 고치지 않았습니다
- 담당이 나뉜 팀에 C를 고른 앞의 초안은 근거가 약해졌습니다

한 번 쓰는 파일 수는 직접 세었습니다. 요청의 수와 순서는 제가 정한 것이고, 설계마다 1번씩 돌린 결과입니다.

## 실행 기록
- 시작 앱은 세 설계 모두 숨은 테스트 44개를 통과했다
- 설계 C를 만들 때 에이전트가 옮기기 전 파일을 지우지 못해 타입 오류가 남았다. 쓰지 않는 파일이라 직접 지우고 다시 확인했다
- 장면 1의 테스트 1개 실패는 세 설계 모두 같다. 요청대로 넣은 `오늘 0:00`이 화면에 두 번 나와 테스트가 찾지 못한 것으로 보인다
- 장면 3의 B · C 병합본은 테스트 8개가 실패했다. 칩 글자가 `✓수학`이 되어 테스트가 찾지 못한 것이고, ✓만 빼면 8개 모두 통과하는 것을 B에서 확인했다. A는 충돌로 병합본을 실행하지 않았다
- 장면 5 첫 실행은 `git rm` 권한이 막혀 파일이 지워지지 않아, 권한을 고쳐 세 설계 모두 다시 돌렸다
- 장면 3의 A는 첫 실행에서 세션 하나가 오류로 끝나 다시 돌렸다. 두 번 모두 같은 두 파일에서 충돌했다

## 한계
실제 리뷰 대기 시간이나 팀원이 느끼는 답답함은 이 실험으로 볼 수 없습니다. 또 에이전트는 사람 팀처럼 일하지 않아서, 일하는 방식을 글로 적어 줘도 그것은 흉내일 뿐입니다. 여기서 확인되는 것은 "이 방식에 맞춘 환경이 코드에 어떤 차이를 남기는가"까지입니다.

- 설계마다 1번씩 만든 코드라, 차이가 설계 때문인지 에이전트가 그렇게 쓴 탓인지 완전히 나누기 어렵습니다
- 장면 3의 요청은 두 사람이 같은 공통 컴포넌트를 건드리도록 일부러 골랐습니다
