# 실험 2: 공통 모듈

> 2026-11-03 사용자 확인. 시험 실행 없이 3번만 돌린다.

## 질문
- 작은 프로젝트에서 공통 모듈을 언제, 어떻게 만들어야 작업과 유지보수가 가장 효율적인가?

## 고정값
- 디자인 시스템: 토큰 + 컴포넌트 (앞 실험에서 일관성이 가장 낫고 빠른 구성)
- 모델: Sonnet 5.5, effort low, Max 구독으로 실행
- 시안 · 패널 · SDD · 엔티티 · 기본 게이트 · 가짜 API는 앞 실험과 같다
- 단계마다 새 세션으로 시작한다

## 비교 조건 (각 1회, 총 3번)

| 조건 | 공통 모듈 | 안내 |
|---|---|---|
| A | 없음 | 없음 |
| B | 미리 제공 | API · 과목 목록 · 이름 규칙 · 오프라인 |
| C | 에이전트가 추출 | 두 화면 이상에 쓰면 공통으로 옮긴다 |

## 단계

| 단계 | 할 일 | 채점 |
|---|---|---|
| 1~3 | 앞 실험과 같은 화면 3개 | 44개 |
| 4 | 규칙 변경: 이름 최대 15자 → 12자 | 5개 + 44개 재검사 |
| 5 | API 변경: `/api` → `/api/v2` | 49개를 새 경로로 재검사 |

- 4 · 5단계에서는 게이트의 테스트와 가짜 서버도 새 값으로 바꾼다
- 공통 모듈은 에이전트가 한 번 만들고, 비용을 B의 환경 비용으로 적는다
- 픽셀 차이와 접근성은 앞 실험과 같은 구성이라 비교하지 않는다

## 비교하는 것

| 관점 | 지표 |
|---|---|
| 에이전트 | 정답률 · 비용 · 시간 · 턴 |
| 생산성 | 새 화면 1개 시간 · 비용, 환경 만드는 비용 |
| 개발자 | 변경에 수정한 파일 수, 변경 적용률 |
| 유지보수 | 중복: API 호출 위치 · 이름 규칙 위치 수 |
| 읽기 쉬움 | 변경 전에 읽은 파일 수 |
| 사람 판단 | 결과 코드를 사용자가 보고 1~5점 |

## 한계
- 조건마다 1회라 큰 차이만 가려낸다. 작은 차이는 판단하지 않는다
- 변경 요청 2개로는 오래 쓰는 프로젝트의 유지보수까지 비교하지 못한다
